# Atlas researcher-acceptance protocol

This protocol is the evidence gate for any claim that Atlas is an 8/10 cross-community fundamental-research discovery tool. Passing tests, a successful API response, a high result count, or a polished summary is not a substitute for this review. Until the measurements below are complete and independently checked, Atlas must not be assigned that score.

## Scope

Evaluate the deployed search workflow—not mocked components—across eight current language/community lenses: English baseline, Korean, Japanese, German, French, Brazilian Portuguese, Hindi, and Spanish. These are search lenses, not verified national populations. The English baseline is not a U.S. sample. Do not phrase a result as a country's view unless contributor geography is independently verified (the current configured providers generally do not verify it).

Use ten varied market topics, selected before testing: two company/issuer topics, two commodities or agricultural inputs, two consumer/industrial product markets, two macro/financial conditions, and two topics chosen by reviewers to expose ambiguity or low-volume coverage. Avoid choosing topics because Atlas already returns strong results. Record the exact baseline and local-language query used; a fluent reviewer must approve each local phrase before search. Run each topic/lens pair three times on separate days to expose freshness and provider variability: 240 searches total.

## Record review

The collapsed **Search audit** section beneath the results provides a local JSON observation log. Use it to transcribe exact queries, source states/counts, UTC times, citation references, overview-input selection, and the deployment commit into the worksheets. It does not contain reviewer labels, source text, original URLs, summary wording, or supporting quotes and cannot be passed directly to `evaluate:acceptance`. Review originals and claim wording in the open search before closing it. Pseudonymous original-record fingerprints are stable only within that search; the private salt stays in page memory, so these fingerprints must not be used for cross-run identity tracking. A null deployment commit means the environment did not supply verified-format build metadata; establish the actual deployed commit independently rather than inventing one. The JSON contains user-entered search phrases: review them before sharing or committing the file. No acceptance gate is satisfied merely by downloading observations.

For each search, preserve the app's source-specific raw-return count, accepted-result count, excluded-result count, exact baseline/local query text, UTC run time, provider status, language lens, and deployed commit. Review a deterministic random sample of up to ten results per provider per search; if fewer than ten are returned, review all. Open the original source. Reviewers may record only a source key, result/citation ID, and labels—do not copy post text, author handles, email addresses, or private profile information into the worksheet. All rows must refer to the same deployed commit.

Use the exact provider status: `complete`, `partial`, `unavailable`, or `not-searched`. For complete/partial sources, counts must be measured nonnegative integers, including zero for a successful empty response. For unavailable/unsearched sources, leave all three count cells blank: the app's null observation is unknown, not a measured zero. Do not attach sampled results to those sources. The operator-breadth report separates known high-volume searches from searches whose discussion volume could exceed the ten-record threshold if an unavailable source were measured. It includes the latter in a conservative denominator; a lower bound below 70% is insufficient evidence, not a passing score. No statistical confidence interval is assigned to that missing-data lower bound.

The worksheet importer requires every canonical column, rejects duplicate or blank headers and malformed CSV even in header-only files, and accepts only `yes`, `no`, or blank for binary labels. Extra template columns are supported but discarded before evaluation. Import errors withhold record contents. Keep the canonical headers unchanged; a header-only template represents no review evidence and cannot pass acceptance.

Use the three normalized templates: [source/run observations](researcher-acceptance-source-runs.csv) (one row per provider per search), [sampled result reviews](researcher-acceptance-results.csv) (one row per sampled result), and [summary claim reviews](researcher-acceptance-claims.csv) (one row per claim). The result sheet records whether Atlas returned the item, whether it was actually selected into the overview, and whether Atlas flagged a duplicate; reviewers record their labels independently, and separate adjudicated fields are required for precision and duplicate recall. Mark `adjudicated_duplicate` yes/no for every sampled result; when yes, assign a stable duplicate-group ID shared by at least two reviewed rows within that run. Group IDs must contain no author or text data. For a provider with no results, still record its status and measured zero or unknown blank counts as specified above. In the claim sheet set `claim_type` to `overview` or `comparison`; label both-sides citation only for comparison claims. Use only `yes` or `no` for binary labels; leave a field blank only when it does not apply or has not yet been reviewed.

Two reviewers label each sampled result independently. At least one reviewer must be fluent in the language of the item; machine translation alone is not sufficient for relevance or meaning labels. Resolve disagreements with a third reviewer or record them as unresolved. For every item, label: topic match; substantive market relevance; language-label correctness; first-person/community opinion versus linked/reported material; likely promotion/spam; duplicate/near-duplicate of another sampled source; original link accessible; and whether the displayed source/lens wording makes a geographic claim it cannot support.

## Summary review

The overview can contain up to three separately rendered claims per searched side, each with its own citation links and quote disclosure; the comparison remains one cautious claim. Review and label each observation separately, not the combined passage as one claim. The local audit's `summary.claims` provides per-search IDs such as `baseline-1`, citation IDs and quote counts, and each record's `citedByClaims` links back to those IDs. It deliberately omits claim prose and quote text. Deterministic fallback passages are not emitted as AI claim identities. Separate claims, platform labels, and citation counts do not themselves establish source independence, agreement or representative coverage.

For each generated overview, label every claim against its cited original sources: citation resolves; exact supporting excerpt is present; excerpt semantically supports the full claim; the text describes a post as a post rather than asserting it as fact; the claim does not infer author nationality/residence from language or server; the comparison cites both searched sides; and material counter-evidence is not omitted when it appears in the sampled evidence. Review at least ten claims per language lens across at least five topics and two run dates, including at least one two-sided comparison claim for every non-English lens. Both reviewers independently label resolvability, exact quote, semantic support, and unsupported geography; adjudicate the final labels. Record unsupported, overstated, contradicted, or geographically overclaimed statements as failures, not as stylistic disagreements.

If AI is unavailable, assess the deterministic overview separately and do not count it as an AI summary. If the result set is empty, label provider status and treat it as a coverage observation only—not proof that the topic or view is absent.

Semantic support includes temporal meaning. A recently published post is not necessarily about current conditions: it can discuss a historical episode, forecast, hypothetical or analogy. A summary that removes a necessary historical actor/period, turns a forecast into an observed outcome, assigns an event date from a posting timestamp, or presents historical figures as current fails the existing semantic-support label. Unknown event timing must remain unknown; `reportedPostedAt` is unverified provider/client posting metadata, not an independently established event date. Include these cases in the preselected ambiguity/stress topics and review the full excerpt/original, not merely the model's chosen quote. Historical analogies may be relevant and should not be rejected merely for being historical; assess whether the summary preserves their actual role and uncertainty. The temporal prompt and timestamp plumbing do not satisfy this human review requirement.

## Minimum acceptance gates

All gates must pass; report sample sizes and confidence intervals alongside rates. Do not pool language results to hide a failing lens.

1. At least 50 independently reviewed result records per language lens, from at least five topics and two separate run dates. Fewer records means that lens is unvalidated, not a pass.
2. Inter-reviewer agreement (Cohen's kappa) of at least 0.70 on topic match, market relevance, and geographic overclaim labels before adjudication. Lower agreement means the rubric or labels are not reliable enough to score Atlas.
3. At least 80% precision for items labeled both on-topic and substantively market-relevant overall, and at least 70% for every language lens. Publish per-provider and per-lens denominators; a source with fewer than 20 reviewed items is “insufficient sample,” not a pass.
4. At least 90% of summary claims are judged semantically supported by their cited source(s), with 100% of citations resolvable and zero unsupported country/nationality claims. Exact quote matching is a structural safeguard and does not itself pass semantic support.
5. At least 90% recall and at least 90% precision for duplicate flags on the reviewed sample, with no duplicate source item counted as independent corroboration after Atlas's cross-source deduplication. Excessive false-positive collapse fails this gate; report both denominators separately.
6. At least two genuinely distinct community operators contribute usable discussion to 70% of topic/lens runs that have ten or more raw discussion results across configured providers. Only accepted, on-topic, market-relevant, correctly language-labeled, accessible, non-promotional original opinions with a negative duplicate label count; reporting and other non-discussion providers never contribute. Multiple instances of one federated network count as one operator. Runs below the threshold must be visibly described as single-platform or thin coverage.
7. Every observed missing, stale, inaccessible, rate-limited, or partial provider state is represented accurately in the UI; zero-result searches are never described as evidence of absence.
8. Adjudicated language-label accuracy is at least 90% in every lens, based on at least 50 reviewed records per lens. Do not pool lenses to hide a weak language classifier.
9. Evidence lineage is internally consistent: no duplicate source-provider, result, or claim identities; every result and summary claim links to a recorded search; topic, language lens, source operator, and deployed commit agree across linked rows; the study covers exactly one deployed commit; and every reviewer-confirmed duplicate group contains at least two sampled records.
10. Every overview input is on-topic, market-relevant, correctly language-labeled, an original community opinion rather than promotion/spam, and not marked as a duplicate; no adjudicated duplicate group contributes more than one overview input. Require at least ten selected overview excerpts per lens across at least five topics and two dates.
11. At least 95% of sampled original-source links resolve, with at least 50 reviewed links per lens and no missing link-access labels.

These are minimum product gates, not a universal investment-research standard. A passing result would support—not guarantee—an 8/10 rating for this bounded use case. Investment performance, causal inference, and representativeness require different studies and are outside this protocol.

## Evidence package

After completing the three sheets, run `npm run evaluate:acceptance`. The evaluator reports each gate as pass, fail, or insufficient; calculates Cohen's κ and Wilson 95% intervals; and emits per-provider/per-lens denominators, including summary quality per lens. Exit code 0 means the recorded evidence passes every configured gate; exit code 2 means it does not. The report is a calculation aid, not proof that entries are accurate or that the sample was drawn as specified.

Keep the completed sheets, generated anonymized aggregate report, reviewer qualifications by language (not names unless they consent), disagreements/adjudications, exact deployed commit, run dates, source statuses, and any failures. Do not publish or commit source excerpts, account handles, or private personal information. A rating is permitted only after all gates pass on the same deployed version and an independent researcher signs off on the interpretation.

The blank templates contain no user-content fields and are safe to commit. They are evaluation aids, not acceptance evidence.
